Discussion / Introduction 
The city has been dealing with a rise in traffic incidents and road accidents, and the city council 
wanted to do something about it. Their solution was to build a database that keeps track of every 
driver in the city including things like where they work, the areas they drive through most often, and 
whether they have received any traffic tickets. If a driver has a ticket, the system needs to store 
exactly when it was issued and where it happened. Having all of this in one place gives the city a 
much better picture of who is on the roads and where problems are most likely to come from. 
 
The goal of this project is to build that driver database system in a way that is organized and 
efficient. Our program will start by reading in at least 100 driver records from a text file and loading 
them into the system. From there, the user will get a menu where they can: add new drivers, search 
for a specific driver by their ID, pull up the most recently licensed drivers, pull up the oldest licensed 
drivers, or move a driver to an inactive database if they leave the city. The system keeps two 
separate lists — one for active drivers and one for inactive ones — so records are never deleted. 
 
System Requirements 
• To store all the information about a driver, the program uses a base class called Driver that 
holds things like the driver’s name, date of birth, address, license issue date, work category, 
years of experience, medical condition, and ticket details.  
• Instead of storing things like dates and addresses as plain text strings, our program uses 
separate classes for them. A Data Class, an Address class, and a Ticket class which will be 
inside the Driver class (composition).  
• On top of that, three classes called YouthDriver, MiddleAgeDriver, and SeniorDriver are built 
off the base Driver class using inheritance, since the city wants us to also classify drivers by 
age group (16-28 as youth, 28-50 as middle-aged, and 50+ as senior).  
• For actually storing and managing all the driver records, our program uses 4 different data 
structures (built from scratch without using any STL of course).  
• The linked list holds all the active driver records and makes it easy to insert drivers at the 
beginning, middle, or end of the list.  
• Our hash table will work with the linked list and will let the program find any driver by their ID 
in O(1) time, meaning it won’t have to scan through the whole list to find someone.  
• We used a stack to track the newest licenses because they work as LIFO (last in first out), so 
popping off the top N items will give us the most recently added licenses.  
• The queue we used does FIFO (first in first out), so it tracks the oldest licences, pulling from 
the front and giving access to the licences that have been in the system the longest.  
• Lastly, a second linked list will handle inactive drivers separately.  
 
 
 
Class Structure Driver: Abstract base class with all common fields. 
YouthDriver, MiddleAgeDriver, SeniorDriver: Derived via inheritance. 
Composition classes: Date, Address, Ticket (nested inside Driver). 
Data Structures LinkedList: Holds active driver records; supports front, back, and mid insert. 
HashTable: O(1) driver lookup by ID using chaining with a linked list. 
Stack (LIFO): Tracks newly licensed drivers for newest-first retrieval. 
Queue (FIFO): Tracks oldest licensed drivers for oldest-first retrieval. 
Second LinkedList: Manages inactive driver records separately. 
Key Constraints Minimum 100 driver records loaded from a text file at startup. 
All data structures built from scratch — no STL containers. 
Records are never deleted; inactive drivers move to the inactive list.

HashTable 
Provides O(1) average-case lookup by driver ID. Uses a character-sum hash function and chaining 
(via an array of linked lists) to resolve collisions. The table size is fixed at 101 slots to minimize 
collisions while keeping memory use reasonable. 
HashTable

Algorithms 
The pseudocode below describes the core operations performed by the system. 
Add Driver 
Algorithm AddDriver(d) 
  Insert driver into activeList 
  Insert driver into lookupTable 
  Push driver onto recentStack 
  Enqueue driver into processQueue 
 
 
Search Driver 
Algorithm SearchDriver(id) 
  index <- hash(id) 
  Go to lookupTable[index] 
  Traverse linked list in that bucket 
  IF driver with matching id found 
    RETURN driver 
  ELSE 
    RETURN null 
 
Deactivate Driver 
Algorithm DeactivateDriver(id) 
  driver <- SearchDriver(id) 
  IF driver = null 
    RETURN false 
  Remove driver from activeList 
  Remove driver from lookupTable 
  Insert driver into inactiveList 
  RETURN true 
 
Retrieve N Newest Licensed Drivers 
Algorithm GetNewestLicensed(n) 
  Create empty list result 
  count <- 0 
  WHILE stack not empty AND count < n 
    driver <- pop recentStack 
    Add driver to result 
    count <- count + 1 
  END WHILE 
  RETURN result 
 
 
 
 
Retrieve N Oldest Licensed Drivers 
Algorithm GetOldestLicensed(n) 
  Create empty list result 
  count <- 0 
  WHILE queue not empty AND count < n 
    driver <- dequeue processQueue 
    Add driver to result 
    count <- count + 1 
  END WHILE 
  RETURN result 
 
Hash Function 
Algorithm Hash(id) 
  sum <- 0 
  FOR each character c in id 
    sum <- sum + ASCII(c) 
  END FOR 
  index <- sum mod TABLE_SIZE 
  RETURN index
